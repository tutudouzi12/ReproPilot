# 设计说明与已知限制

本文用较少的术语说明 ReproPilot 为什么采用当前设计，以及它目前不能解决什么。

## 1. 为什么把任务拆成流程

论文与代码实验通常包含准备仓库、修改代码、运行评测和整理结果等多个步骤。ReproPilot 将这些步骤组织成带先后关系的执行计划，再交给不同 Agent 处理。

这样做的好处是任务进度更清楚，某一步失败时可以定位到具体节点，也便于重试或继续未完成的任务。代价是新增任务类型时需要先定义流程，灵活性低于完全自由的模型对话。

## 2. 为什么限制模型的权限

模型适合分析问题和提出候选修改，但不应该同时负责修改评测规则、运行代码并宣布自己成功。因此系统会限制可修改文件，并由普通程序负责执行命令、计算结果和决定是否保留修改。

这种方式更容易检查实验过程，但要求任务本身存在明确的评测方法。对于没有客观指标的开放研究问题，系统只能辅助整理过程，不能自动判断科学结论是否正确。

## 3. 为什么使用 Docker 执行代码

外部仓库可能包含未知依赖或有风险的命令。ReproPilot 将代码实验放进独立容器，并限制资源、网络、运行时间和输出大小，任务结束后清理容器。

Docker 可以降低对本机环境的影响，但不是绝对安全边界。当前实现适合个人本地研究和受控代码，不适合直接开放给不可信公网用户。

## 4. 为什么保存实验记录

模型生成的总结可能遗漏失败过程，也可能错误理解运行结果。系统会保存任务配置、候选修改、命令结果和验收报告，让最终结论可以回到实际产物进行检查。

记录完整过程能够提高可追溯性，但不代表实验结果天然正确。代码通过既定评测，只说明当前任务要求被满足，不能自动证明论文结论被完整复现。

## 当前范围

- 面向个人使用的单机研究执行系统，不是生产级分布式平台；
- 支持多 Agent 分工，但重点是流程与权限边界，不是 Agent 数量；
- 支持受控代码实验，但不保证修复任意仓库或复现任意论文；
- 已包含自动化测试与 Docker 检查，但仍需继续补充前端测试和浏览器端到端测试。
